What this guide covers

This explains the main source files and how they work together. It focuses on the code that makes the product run, rather than repeating every CSS declaration or every test case line by line.

Project in one minute

HavenStay is an accommodation search and booking-request website. The frontend is JavaScript built with Vite. It calls a Node.js/Express backend using HTTP and JSON. The backend is organized into four logical services: Listing, Search, Availability and Booking. Mongoose connects those services to MongoDB.

Docker Compose starts three containers locally: the Nginx frontend, the API and MongoDB. The MongoDB container is configured as a one-node replica set so that booking transactions work.

2 · Frontend startup and routing

frontend/index.html and src/main.js

index.html — the browser entry page

Defines the page metadata, HavenStay name, header navigation, menu button, main content region, footer and module script. The main element is empty at first; JavaScript renders the active page into it. Navigation links use hash routes such as #/, #/host and #/listing/ID.

main.js — application coordinator

Imports the UI styles and modules, creates the API client, finds the main element and keeps route state. A hashchange listener calls route(). The router chooses Home, Host, Saved/Compare, Listing, Booking lookup, Booking details or Management, then renders the matching view.

It also contains the homepage and property-detail rendering, result loading, search/form event handlers, booking confirmation and cancellation, navigation menu behavior, share/copy helpers, and safe image fallback behavior.

Route examples

#/ discovery · #/listing/abc... property details · #/booking find a booking · #/booking/abc... booking details · #/saved saved stays · #/compare comparison · #/host publish a listing · #/manage manager workflow.

Why route versions and abort signals exist

Users can navigate away while an HTTP request is still running. A route-version check stops an old response replacing the new page. An AbortController cancels obsolete search requests so outdated results do not flash on screen.

Page rendering and safe text

Templates insert database values into HTML. The shared escapeHtml helper escapes characters such as < and quotes before user-provided text is displayed. Image URLs are separately checked before use.

Other root frontend files

vite.config-style setup is in package scripts; playwright.config.js starts Vite for browser tests. public/ stores image assets that are copied into the final static build.

4 · Frontend styles and user flows

CSS files and a search request

Stylesheets

style.css contains base layout, typography, forms, cards and responsive defaults. airbnb.css contains inherited project visual styles and layout rules. experience.css styles discovery, calendar, host, manager and interactive details. havenstay.css provides HavenStay brand overrides and responsive refinements. CSS order matters: later rules can override earlier rules.

Search flow

  1. User enters a destination and filters.
  2. main.js combines values from the search and filter forms.
  3. discovery.js may resolve the typed destination to a canonical city and country.
  4. The browser sends GET /api/search?...&page=1&limit=8.
  5. The page displays stay cards and pagination using the returned data and metadata.

Details and booking flow

  1. Opening a stay calls GET /api/listings/:id and requests upcoming reserved ranges.
  2. The calendar helps select check-in/check-out; the form can check availability.
  3. Client validation catches missing or impossible dates before submission.
  4. The frontend creates a stable idempotency key, then sends guest details, listing ID and dates to POST /api/bookings.
  5. The backend validates again, calculates the price itself and returns the booking reference/status.
  6. The confirmation route loads current status by reference; guests can refresh, print, export calendar event or cancel.

Client validation is not the security boundary

Browser checks improve the experience, but requests can be changed or sent without the website. The backend repeats all important validation and enforces availability in MongoDB.

The same API client is used by search, details, listing forms, booking and management screens.

5 · Backend startup and HTTP application

backend/src/server.js and app.js

server.js — process startup

  1. Loads environment configuration.
  2. Connects to MongoDB and waits for model indexes.
  3. Stops startup if the database cannot support required transactions.
  4. Builds the Express app and starts listening on the configured port, normally 5000.
  5. On SIGINT/SIGTERM, stops accepting HTTP work and closes the database connection cleanly.

app.js — middleware and endpoint wiring

Creates an Express app, hides the Express signature header, trusts the first reverse proxy hop, then applies request metrics, Helmet security headers, CORS, and a small JSON-body parser. It mounts the API router at /api.

The health route /health (also /api/health) reports whether MongoDB is connected. If the database is down, it returns HTTP 503, which lets Docker or a load balancer avoid sending traffic to an unhealthy backend.

Unknown endpoints flow to notFound.js. Errors flow to errorHandler.js. Keeping those handlers at the end ensures consistent responses.

Configuration and database connection

config/env.js reads environment variables and optional backend/.env. It selects the normal or test database, parses CORS origins and port, and bounds the Mongo connection pool setting. config/db.js connects through Mongoose, checks MongoDB reports a replica-set or sharded topology, and initializes model indexes before traffic is accepted.

Why refuse standalone MongoDB? Booking transactions and the atomic night-reservation design depend on MongoDB transaction support. Silently running without it could break booking correctness.
6 · Routes, controllers and services

How backend requests are handled

Routes: backend/src/routes/index.js

Defines the URL map and connects each HTTP method/path to a controller. It separates listing, search, availability, booking and admin routers. Confirmation and admin actions use the access-control middleware.

EndpointPurpose
GET /api/listingsPage through listings.
GET /api/listings/:idFetch one listing.
POST /api/listingsCreate a listing.
GET /api/searchSearch and filter stays.
GET /api/availabilityCheck a listing/date range.
GET /api/availability/:id/bookingsGet public booked date ranges for the calendar.

GET /api/bookings/:idLook up booking status/details.

Controllers

listing.controller.js, search.controller.js, availability.controller.js and booking.controller.js adapt HTTP requests to service calls. They read path/query/body values, invoke validation/service logic, and send a JSON response. They should stay thin and avoid owning the business rules.

Services

listing.service.js

Reads, paginates and creates listings. It filters submitted properties through a writable-field list.

search.service.js

Builds safe Mongo filters, sorting and pagination. If dates are included, it asks Availability for unavailable listing IDs.

availability.service.js

Finds active bookings that overlap requested dates and returns safe date-only ranges.

booking.service.js

Checks the listing, capacity and conflicts; reserves individual nights; creates booking and transitions status safely.

The code uses controller → service → model layering. Services can call another service directly, which is called service composition here.

7 · Data models and validation

What MongoDB stores

Model / collectionImportant fields and purpose
Listing.js / listingsProperty title, description, type, city/area/country, nightly price, capacity, bedrooms/bathrooms, amenities, image URLs and rating. Schema rules require key fields, limit values and allow only known property types.
Booking.js / bookingsListing reference, guest name/email, check-in/out, guests, nights, saved booking-time price, total and Pending/Confirmed/Cancelled status. The price snapshot stops future listing price changes altering an existing booking.
BookedNight.js / bookednightsOne record per held night: listing ID, date and booking ID. A unique index on listing+night is the final double-booking guard.

Indexes

Indexes speed up common searches and add database rules. Listings index city/price/type/capacity/creation time. Bookings index listing/status/date fields for overlap checks, guest email/time for lookup patterns, and idempotency hash uniquely when present. Booked nights uniquely index { listingId, night }.

Validators

  • validators/common.js parses strict YYYY-MM-DD UTC dates, rejects impossible/past dates and limits a stay to 30 nights.
  • booking.validator.js checks JSON shape, ObjectId syntax, guest name/email, positive guest count, date range and allowed status transition values.
  • search.validator.js validates optional query strings, numeric price bounds, type, guest count, amenities, sorting and paired dates.
  • availability.validator.js requires a valid listing ID and date range.
  • Model-level Mongoose validation repeats field constraints when data is written.

Shared utility files

utils/dates.js performs date-only math in UTC and lists each occupied night. utils/pagination.js applies safe defaults and a maximum page size. utils/response.js creates the standard success envelope. utils/ApiError.js represents known HTTP errors. validateObjectId.js checks Mongo ID format. databaseName.js safely extracts the database name for environment guards.

8 · Booking correctness, step by step

Why concurrent booking is safe

A simple “check dates, then insert booking” has a race condition: two guests can both check before either one saves. This project does a pre-check for a friendly message, then relies on a unique database constraint and transaction for correctness.

  1. Validate input: make sure listing ID, guest details, guest count and dates are valid.
  2. Read listing: check it exists, price is usable and capacity is large enough.
  3. Pre-check: look for overlapping Pending/Confirmed bookings.
  4. Start transaction: create one BookedNight document for each night in [check-in, check-out).
  5. Save booking: create the booking and its price snapshot; save replay data if a key was supplied.
  6. Commit: all writes become visible together. Any error rolls all of them back.

Example: 10–12 June

Occupied nights are 10 June and 11 June. The 12 June check-out date is free for a new guest to check in. This half-open date interval also makes adjacent stays possible.

What happens in a race?

If another request inserts one of the same listing-night pairs first, MongoDB rejects the unique-key collision. The transaction aborts, so the losing request leaves no partial nights or booking behind. The API returns a conflict, normally HTTP 409.

Idempotency: safe retry after a lost response

The client sends an Idempotency-Key. The backend stores a SHA-256 hash of that key, a fingerprint of normalized booking fields, and the original response. Repeating the same key with the same request returns the original result. Reusing it with different details returns an idempotency mismatch. The raw key is not stored; guest text is not part of the key index.

Cancellation and status rules

New booking status is Pending and it holds nights. Pending may become Confirmed or Cancelled. Confirmed may become Cancelled. Cancelled is terminal. Cancellation status and night-lock deletion happen in one transaction. A repeated cancellation is safe to repeat.

Files to remember: booking.service.js contains the workflow; transaction.js wraps Mongo transactions; BookedNight.js defines the unique lock; Booking.js defines statuses and idempotency fields.
9 · Middleware and API safety

Errors, access and monitoring

Consistent errors

notFound.js turns unmatched URLs into a 404. errorHandler.js maps validation, bad JSON, oversized body, CORS, Mongo connection and unexpected errors to a standard JSON response. It logs unexpected server errors but does not expose stack traces to the browser.

Successful responses use { success: true, data, meta? }. Errors use { success: false, error: { code, message, details? } }. Search/list endpoints include pagination metadata such as page, limit, total and total pages.

Management access

requireAdmin.js protects manager endpoints. The secret token is configured on the server only and must be at least 32 characters. The browser sends it as a Bearer authorization header for that manager session. The comparison uses hashes and a timing-safe check. Never put this value in a VITE_ frontend variable.

HTTP protections

  • Helmet adds security headers.
  • CORS allows configured frontend origins and required headers.
  • JSON bodies are capped at 10 KB in Express.
  • Listing writes copy only an explicit set of allowed fields.
  • Search text is escaped before becoming a regular expression.
  • Object IDs, dates, numeric ranges and enum values are checked.

Metrics middleware

middleware/metrics.js optionally emits JSON metrics with service name, method, status, elapsed milliseconds, request ID and counts for requests/errors/booking conflicts. It avoids putting guest emails, booking IDs or bodies in metric dimensions. It is enabled in local Compose and can be collected by CloudWatch in the planned AWS environment.

Database initialization

models/index.js registers Listing, Booking and BookedNight so Mongoose creates their indexes before startup is considered ready. Unique indexes are part of booking correctness, not just a speed improvement.

10 · Docker basics

What containerization means

A container is a packaged process with its application and needed libraries. Docker images are the blueprints. Containers are running copies of those images. Docker Compose describes how multiple containers connect.

backend/Dockerfile

  1. Starts from a small Node 22 Linux image.
  2. Uses /app as the working directory.
  3. Copies package manifests and runs npm ci --omit=dev so only production dependencies are installed.
  4. Copies backend source/scripts into the image.
  5. Runs as the non-root node user.
  6. Sets production environment/port, exposes port 5000 inside the container, and defines a health check.
  7. Starts with node src/server.js.

frontend/Dockerfile — two-stage build

  1. Build stage uses Node, installs dependencies, copies frontend source/public assets, and runs Vite production build.
  2. VITE_API_URL=/ compiles same-origin API requests into the static site.
  3. Runtime stage uses the smaller Nginx unprivileged image.
  4. Copies only built static files and Nginx configuration into the final image. Node/npm are not needed to serve the finished files.

Why multi-stage?

The build needs compilers and development packages; the running website only needs static files. Keeping only Nginx and those files makes the final frontend image smaller and reduces what is present at runtime.

Image versus container: Dockerfile → build image → start container. Rebuilding creates a new image; Compose can recreate its container from that image.

.dockerignore prevents folders such as node_modules, dist, tests, local environment files and Git data from being copied into Docker build context. This keeps builds lean and avoids accidentally shipping local secrets.

11 · Docker Compose and Nginx

How the local containers cooperate

docker-compose.yml

  • mongo: MongoDB 8.2 starts with replica set name rs0. A named volume mongo-data keeps database files across container replacement.
  • mongo-init: waits for Mongo health, initializes the replica set if needed, then waits for it to elect a writable primary.
  • backend: builds the API image and connects to mongodb://mongo:27017/... ?replicaSet=rs0 using the Compose service name as a private DNS name. It waits until initialization completes.
  • frontend: builds the frontend with VITE_API_URL=/, waits for backend health, and publishes container port 8080 only to host loopback at localhost:8080.

frontend/nginx.conf

Nginx serves built files from /usr/share/nginx/html. Requests to /api/... or /health are forwarded to http://backend:5000. Other paths serve the single-page app entry point. The browser only sees localhost:8080; it must not call the Docker-only name backend.

Network, port, volume and health

Compose automatically creates a private network and DNS entries by service name. Only frontend port 8080 is published to the host. Mongo has no public host port in this file. The named volume stores database records. Health checks and depends_on help services start in the right order.

Data persistence: Restarting/recreating containers does not remove the named volume. docker compose down keeps it. Adding -v to down removes the volume and deletes that local database.

Typical local Docker commands (PowerShell)

docker compose up --build -d builds/starts containers. docker compose ps shows status. docker compose logs --tail 50 backend reads API logs. docker compose exec backend node scripts/seed.js --force loads sample records and replaces records in this project database—only use when that reset is intended. docker compose down stops containers but preserves data volume.

Manual development commands

Backend: install dependencies, configure a replica-set MongoDB URI, seed only if desired, then run npm run dev. Frontend: install dependencies, set VITE_API_URL=http://localhost:5000, then run npm run dev. The browser opens Vite at localhost:5173 and calls backend port 5000.

Seed files

backend/scripts/seedData.js contains sample listings. seed.js connects, clears listings/bookings/night locks, inserts listings, then creates sample bookings through the real Booking Service so reservations follow the same rules. It refuses production seeding unless explicitly forced.

Production guard: Never seed a database with data you need to keep. Read the database name and connection configuration before running seed or test commands.

Planned AWS request path

HTTPS browser → Application Load Balancer → Nginx frontend container → local API container → shared persistent MongoDB. The load balancer can spread traffic across EC2 instances. The instances should not each keep their own copy of booking state.

What production still needs

A chosen persistent MongoDB provider/topology, backups and restore testing, VPC/subnet IDs, TLS certificate, private secret, container images in a registry, IAM review, actual deployment, monitoring evidence and load testing. One-node local replica set is suitable for transaction testing, not highly available production data.

Be precise in a presentation: “We prepared an AWS architecture and deployment template” is true. “We deployed this to AWS” is not currently true.
14 · Testing and quality

How the code is checked

Backend tests

backend/tests/ contains API and service tests for listing, search, availability, bookings, validation, transaction behavior, retries and metrics. npm test uses Jest/Supertest. npm run test:isolated starts a temporary transaction-capable MongoDB test deployment so the ordinary database is not used.

Frontend tests

frontend/tests/ covers date rules, API payloads, search resolution, photo mapping, saved choices, calendar ranges, safe rendering and booking retry behavior. npm test runs the unit/API tests with Node’s test runner.

frontend/e2e/ uses Playwright to drive browser flows such as search, booking, cancellation, host listing publication, management, mobile layouts and accessibility checks. Run with npm run test:e2e -- --workers=1.

Build and style checks

npm run build compiles the production frontend. npm run format:check checks consistent formatting. Docker’s frontend image runs the same production build during image creation.

Additional verification scripts

The frontend has backend contract and live integration scripts. Root scripts/check-deployment.cjs checks an already running stack. Load-testing scripts are separated from normal demo/test data and require explicit load-test configuration.

Why tests matter

Unit tests check small rules quickly. API tests check HTTP shapes and status codes. Browser tests check user journeys. A production build catches import/compile problems. A smoke test checks a deployed stack from outside.

Do not describe a mocked browser API test as a live cloud test. Each test type proves a different thing.

Five points to remember

  1. Frontend: JavaScript/Vite. Backend: Node/Express. Data: MongoDB/Mongoose.
  2. Listing, Search, Availability and Booking are logical backend modules.
  3. Booking uses a replica-set transaction plus unique per-night index.
  4. Docker Compose connects Nginx, API and Mongo; the volume persists local database data.
  5. AWS infrastructure is prepared, not deployed.
