HavenStay

A simple guide for your 10-minute project viva

Read this first · 60-second introduction
“HavenStay is a web platform for discovering accommodation and sending booking requests. It has a JavaScript frontend and a Node.js/Express backend, organized into Listing, Search, Availability and Booking services. MongoDB stores listings and bookings. Docker Compose runs the app locally, and the cloud design shows how the same app can run behind a load balancer with monitoring and auto scaling.”

What the project does

  • Guests search and filter stays, view details and check available dates.
  • Guests submit a booking request and can look it up or cancel it.
  • Hosts can publish a property; a manager can accept or decline requests.
  • Saved stays and comparisons help guests decide.

Understand the application

Four service responsibilities

Listing

Creates, retrieves and paginates property listings.

Search

Filters stays by destination, price, guests, dates and amenities.

Availability

Shows reserved nights and checks whether chosen dates are free.

Booking

Creates a request, calculates its total and handles status changes or cancellation.

Good viva wording: These are separate service modules in one Express application. They have clear responsibilities and API routes, but they are not four independently deployed microservices.

How booking avoids double-booking

  1. Each booked night is recorded for a listing. Check-out is exclusive, so one guest can leave the same day another arrives.
  2. A unique database index allows only one active reservation for the same listing and night.
  3. MongoDB transaction writes the booking and its reserved nights together. If one write fails, the transaction rolls back.
  4. Overlapping requests receive a conflict response; the frontend does not retry a known conflict.

What is idempotency?

A safe retry of the same booking request should not create a second booking. The frontend reuses an idempotency key; the backend returns the original result for the same key and same request data.

Key words in plain English

TermEasy meaning
REST APIURLs and HTTP methods that let the browser and backend exchange data.
Replica setMongoDB nodes that maintain the same data and support transactions. The local Docker setup uses a one-node replica set for transaction support.
Reverse proxyNginx receives browser traffic and forwards API requests to the backend.
Stateless app serverThe server keeps no essential booking state only in its memory; shared database state lets another app replica continue the work.

Remember: transaction = all related booking writes succeed together, or none do.

Cloud computing connection

How the project runs

EnvironmentWhat it means
Local Docker ComposeRuns frontend, backend and MongoDB containers together. The database volume persists across container restarts.
Cloud designPrepared AWS design: HTTPS load balancer, EC2 Auto Scaling Group, app containers, Secrets Manager and CloudWatch.
Actual deployment statusAWS resources have not been deployed. Say this clearly; the local Docker setup is the running environment.

Cloud ideas to explain

  • Scale out: add more backend instances when demand grows. A load balancer sends requests to healthy instances.
  • Shared state: all backend replicas use the same persistent database, so each sees the same bookings.
  • Health checks: /health tells the platform whether the API and database are ready.
  • Monitoring: CloudWatch is planned for logs, request counts, latency, errors and alarms.
  • Secrets: private manager credentials belong on the server or in a secret store, never in public frontend code.
  • Availability: multiple app instances can reduce downtime, but the database also needs backups and a resilient production topology.

If asked “Is it deployed on AWS?”

“The AWS architecture and infrastructure template are prepared, but AWS resources have not been deployed. I can demonstrate the integrated app locally with Docker Compose. I would deploy only after configuring the VPC, HTTPS certificate, secrets and persistent database.”

Technology at a glance

  • Frontend: JavaScript, Vite and responsive CSS.
  • Backend: Node.js, Express and Mongoose.
  • Data: MongoDB replica set for transaction support.
  • Packaging: Docker images and Docker Compose.
  • Web entry point: Nginx serves the frontend and proxies API paths.

Keep claims accurate: “designed/prepared for AWS” is different from “deployed on AWS.”

Likely viva questions

Short answers to practise

1. What problem does HavenStay solve?
It brings stay discovery, availability checks and booking requests into one simple website.
2. Why did you use a service-oriented design?
It separates the main business responsibilities, making the code easier to understand, change and test.
3. Is each service a microservice?
No. They are logical modules inside one backend application, not separate deployed services.
4. What does Docker do here?
It packages the app and its dependencies into containers so the same setup can run consistently on another machine.
5. Why use MongoDB transactions?
A booking and its reserved nights must be saved together. A transaction prevents partial writes.
6. How do you prevent two guests booking the same dates?
A unique index protects each listing-night pair, and the booking operation uses a transaction. One conflicting request is rejected.
7. What is the role of Nginx?
It serves the built frontend and forwards API requests to Express, so the browser can use one website origin.
8. How would the design scale?
Run more stateless backend replicas behind a load balancer, while they share the same persistent database.
9. What would you monitor?
Request volume, response time, errors, booking conflicts, instance health and database performance.
10. What is a current limitation?
The cloud design is prepared but not deployed; the local database is a single-node replica set, not production high availability.
11. What would you improve before real customers use it?
Add guest and host accounts and authorization, payment handling, a resilient managed database, backups, and a clear price currency.
12. What did you learn?
Cloud apps need more than containers: shared persistent data, safe concurrent writes, health checks, secrets, monitoring and honest deployment verification all matter.

Last-minute reminder

Answer in this order: what it does → how a request flows → how booking data stays correct → how cloud deployment could scale it. Keep each answer to two or three sentences.
